# 直接操作與動畫設計（第二階段補強）

日期：2026-10-21。這份文件補充 `2026-10-19-inference-calculator-design.md`（下稱「主設計」），範圍是網站主畫面（`packages/web`）與 core 的一個新 API。主設計的規則（§2 資料誠信、§8.2 視覺準則、§8.3.3 v6 版面）全部繼續適用；本文只寫新增與改變的部分。

## 1. 為什麼

第二階段的網站完成後，使用者實際操作，指出三個問題：

1. **不能自己調整卡數。** 使用者的原話：「我知道建議值的速度是怎麼樣，但我想知道更多資源下會是甚麼速度，這 web 不符需求。」主設計 §8.1 本來就要求「直接操作：在結果頁可以直接拖拉節點數、人數、上下文長度，即時預覽速度與容量的變化，並保留建議值作為對照」，§8.2-6 也要求「拖拉人數或機器數時，答案句、圖示、體驗指標同步更新，並保留建議值作為對照」。v6 版面與第二階段計畫都漏掉了這一項。
2. **展開／收合是手刻的。** 沒有用 UI 元件庫的元件，違反「UI 一律用元件庫」的要求（主設計 §8.3.3 視覺樣式）。
3. **沒有良好的動畫設計。** 除了機器圖示與記憶體條，其他變化都是直接跳變：答案數字、台數、展開的細節、最佳方案的標記、可行與不可行的切換。主設計 §8.1、§8.2-5 要求「同一批物件因參數改變而變化時，用動畫呈現因果」。

**成功的樣子**：使用者看到建議值後，可以把某個平台的卡數往上或往下調，立刻看到每人速度、首字等待、使用率怎麼變，並且隨時一鍵回到建議值。所有變化都有清楚、一致的動畫，讓人看得出「我改了什麼 → 什麼跟著變」。

## 2. 目標

- G1：「我需要多少」模式中，每個可行的平台列都可以調整卡數（或台數），預設是建議值。
- G2：調整後立刻顯示該卡數下的每人速度、首字等待、使用率與瓶頸，並和建議值並排對照。
- G3：「我已有」模式也能回答「這些卡給 N 人用，速度多快」。
- G4：主畫面所有因輸入改變而產生的變化，都依第 6 節的動畫設計呈現。
- G5：列的展開與收合改用 antd 元件。
- G6：補上主設計 §8 中、v6 版面漏掉且和本次需求直接相關的兩項：細節面板的「每人速度 vs 人數」單軸小圖（§8.3 第 3 列），以及頁面上的語言切換（§8.4）。
- G7：機器圖示與其他視覺元素回到使用者核可的 v7 原型（第 5.6 節）。

## 3. 非目標

- 不做主設計 §8.3 的「量級尺」、「哪個平台划算」排序橫條、專家檢視、引用匯出、HF 匯入、自訂工作負載與速度。這些維持在主設計 §10.2 排序中的後續階段。
- 不調整上下文長度。主設計 §8.1 有提到，但它屬於「自訂工作負載」（第 4 項），留到那時。
- 不改 core 的任何公式或校正值。
- 不改「最佳方案」的定義（仍是國網平台中 GPU 數最少者）。答案行仍然是建議值，不跟著使用者的調整改變。

**反目標**（技術上可行但仍算失敗）：

- 調整卡數時，數字直接跳變、沒有因果動畫。
- 使用者調過之後，看不出現在是不是建議值，或找不到回到建議值的方法。
- 網站自己算速度。速度、首字、使用率一律來自 core（主設計 §10「網站與 MCP 都不得自行實作公式」）。

## 4. core：新 API `estimatePerformance`

輸入：和 `estimateCapacity` 相同的欄位（`model`、`quant`、`workload`、`speed`、`platform`、`gpus`、`includeComm?`），**再加上 `users`**（必填）。`gpus` 對 Mac／DGX Spark 代表台數。

做法：在 `gpus` 張卡內，列出所有合法切法（每副本 t 張，t 依 `legalTpOptions`，副本數 = floor(gpus ÷ t)），以 `checkShape` 在 `users` 人、預期 η 下評估。

**選哪個切法（設計者判斷）**：和建議值用同一套排序，確保數字前後一致：

- 有切法符合速度目標與記憶體：取這些卡的**人數上限最大**的切法；人數上限相同時取 t 較小者。這就是求解器產生建議值時的排序（Ruling R34），也是 `estimateCapacity` 的排序（`maxConcurrentForGpus`）。
- 結果必須滿足：卡數等於建議值時，切法、每人速度、首字與 `estimateRequirements` 該平台的預期結果**完全相同**；「我已有」模式中，速度那一行和「最多 N 人」那一行說的是同一個切法。
- 選「每人速度最快」的切法被否決：它會讓建議值的對照比較的是兩種不同的切法，也會讓多加卡時人數上限反而變小，違反第 6.2 節「多給卡 → 每人變快、可服務人數變多」的因果。
- 沒有切法符合速度目標，但有切法放得下記憶體：依同樣的排序取最好的切法（人數上限都是 0 時，取每人速度最快者），回傳它的數值，並標示 `ok: false` 與 `why`（`bw`／`compute`／`ttft`），讓使用者看到「卡太少時實際會多慢」。
- 連記憶體都放不下、TP 不合法、上下文超過、規模超過上限：回傳 `ok: false`、`why`、`detail`，沒有數值。

回傳（名稱由實作者決定，內容必須包含）：

- `ok`、`why`、`detail`
- 使用的切法（`shape`）
- `usage: ShapeUsage | null`（沿用第二階段的型別：每人速度、首字、四個比例、記憶體組成）
- 這個切法的 `speedCurve`（第 5.4 節的小圖用）：人數範圍是 1 到 max(人數上限, `users`)，所以卡太少時，目前人數仍落在曲線上，人數上限另外標出；記憶體放不下時為 null（**設計者判斷**）
- 只用預期 η。調整過的列不顯示保守估計（不畫虛線圖示、不顯示「保守 N 張」），因為保守值是建議值的屬性，對使用者自選的卡數沒有對應的問題要回答（**設計者判斷**）。未調整的列照舊顯示保守估計。
- `maxConcurrent`（這些卡在速度目標下最多幾人）
- 峰值功耗（`gpus × TDP`，TDP 未查證時為 null 並附說明，規則同 `estimateRequirements`）
- `basis`、`hasEstimate`、`hasUser`、`warnings`、`dataVersion`，規則同其他 API

所有邊界與錯誤規則照 core 既有的慣例：輸入用 zod 驗證，使用者輸入錯誤丟出 `CoreInputError`；單一平台的規模問題用 `why: 'scale'` 回傳，不丟錯。

## 5. 網站

### 5.1 「需要多少」模式：每列的卡數可以調整（使用者指定）

使用者的要求：「可以有個按鈕設成 suggest，預設也是 suggest，但是允許用戶自由調整。」

- 每個可行的平台列，台數旁有一組控制：
  - **「建議」按鈕**：預設是選取狀態，代表這一列顯示建議值。使用者調整過後，按鈕變成未選取；按下去就回到建議值。
  - **數量調整**：antd `InputNumber`（附 − / + 步進鈕），可以直接打字。單位跟著平台：GPU 平台是「張」，Mac／DGX Spark 是「台」。範圍 1 到 100,000。
- 調整的結果：
  - 機器圖示照新的數量重畫。原本的建議數量用一條「建議」刻度或殘影標出（**設計者判斷**：細節由實作者決定，但必須一眼看得出建議值在哪）。
  - 列上**新增**一行速度與首字：「每人 41 字/秒・首字 0.5 秒」，旁邊用小字寫建議值的數字，例如「建議 4 張：27 字/秒・0.8 秒」。只在調整過的列顯示；沒調整的列維持 v6 原則（可行就代表已達標，不顯示速度）。
  - 容量條改用調整後的人數上限。
  - 調整到比建議值少，導致速度或首字不達標：顯示不達標的原因與實際數值，例如「✗ 首字要等 12 秒（目標 5 秒）」。記憶體放不下時只顯示原因。
  - 展開的細節面板（打字示範、使用率條、記憶體條、小圖）全部改用調整後的數值。
- 狀態：每一列的調整值寫進集中的 store，並寫進網址（例如 `o=nano4-h200:8,nano5-h100:16`），可以分享。輸入條件（人數、工作、模型、精度、速度）一改變，所有調整值都清除、回到建議值（**設計者判斷**：建議值本身已經變了，保留舊的調整值會讓對照失去意義）。
- 答案行不變，仍然是建議值。

### 5.2 「我已有」模式：補上人數（設計者判斷）

- 句子改為：「我有 `[數量]` `[張／台]` `[平台 ▾]`，同時最多有 `[人數]` 人會使用，做 `[工作 ▾]` 任務，…」。人數欄與「需要多少」模式共用同一個值。
- 答案行：
  - 主答案：`每人 41 字/秒・首字 0.5 秒`；達不到速度目標時，用紅字寫出原因。
  - 下一行小字：`這些卡最多同時 624 人（保守 …）`。這就是原本的答案。
- 細節面板改用這個人數下的數值（原本是「滿載時」的數值）。

### 5.3 展開／收合改用 antd `Collapse`

- 平台列表改用 antd `Collapse`，設 `accordion`，`activeKey` 由 store 的 `openRow` 控制。
- 只有平台名稱那一塊能點來展開（`collapsible="header"`）。機器圖示、數量控制、容量條放在 header 的其他區域（例如 `extra`），裡面的說明框與輸入框不會被包在展開按鈕裡（第二階段已修過的巢狀互動問題不可再出現）。
- 不可行的列不能展開：`collapsible="disabled"`，並且不顯示箭頭。
- 最佳方案那一列的左側色條與底色，用 antd 的 `styles`／`classNames` 搭配 token 實作。

### 5.4 細節面板加上「每人速度 vs 人數」單軸小圖（主設計 §8.3 第 3 列）

- 每個可行的列都有這張圖，包括沒調整過的列：網站以建議卡數呼叫 `estimatePerformance` 取得曲線（第 4 節保證結果和建議值一致），不需要改 `estimateRequirements`。
- 用 D3 畫一條線：橫軸是同時人數，縱軸是每人每秒字數。資料是 core 的 `speedCurve`。
- 依主設計 §8.3 第 3 列，背景依速度分成流暢／可接受／卡頓三區並以顏色表示，分界取自設定檔的速度預設值（`speedPresets`），顏色取自 antd token。
- 標出：目前人數的位置、速度目標的水平線（例如「流暢：20 字/秒」）、人數上限。
- 只有一個 Y 軸、線性刻度，不需要圖例就能讀懂（主設計 §8.2-2）。
- 調整卡數或人數時，線與標記用第 6 節的動畫過渡到新的位置。

### 5.5 語言切換（主設計 §8.4）

- 頁首加一個 antd `Segmented`：「中文 / English」，對應 store 的 `lang`。
- 設定檔與 core 的文字仍然只有中文，這一點不變（第二階段已記錄的限制）。

### 5.6 機器圖示照 v7 原型（使用者指出不符規格）

第二階段的圖示中，Mac 和 GPU 一樣是藍色，不符合使用者核可的 v7 原型（`docs/prototypes/calculator-demo-v7.html` 的 `Machines`）。

- **GPU 平台**：維持第二階段的「每個 node 一個圖示」，未滿一個 node 時只填滿相應比例，填色 `colorPrimary`（使用者 2026-10-21 確認：「One per node is acceptable」）。這是和 v7（每張 GPU 一個方塊）之間**已核可的差異**。
- **Mac／DGX Spark（以台為單位）**：照 v7，每台一個橫向方塊（20 × 13，圓角 2），填色與外框都是 `colorTextTertiary`（灰色），方塊間距 4。
- 實心是預期數量，虛線外框（`stroke-dasharray 3 2`、無填色）是保守估計多出的數量；外框顏色同該平台的填色。
- 最多畫 16 個方塊，超過時在後面加上 `+N` 文字（`colorTextSecondary`）。
- **不可超出容器**（使用者 2026-10-21 回報的 bug：圖示沒有換行，超出頁面）。放不下時，照使用者指定的方式顯示，取代 `+N`：

  ```
  ▢▢▢▢ … ▢▢▢▢
  \─── × 80 ───/
  ```

  先畫前幾個方塊、一個省略號、再畫最後幾個方塊，維持一行；下方畫一個大括號（D3 path，`colorTextTertiary`）從第一個方塊跨到最後一個，正中央寫總數「× 80」。保守估計不同時寫「× 80（保守 96）」，虛線方塊放在右端。兩側各畫幾個方塊，依 ResizeObserver 量到的容器寬度決定；放得下時不畫大括號與省略號，照常畫出每一個。數量或寬度改變時，兩側方塊、大括號寬度與數字都以動畫過渡。列中的其他元素（台數、小字、容量文字、數量控制、建議動作）同樣必須換行。驗證：390、768、1024、1440 px 寬，搭配大數量（例如 GPU 平台 60 個 node、20 台 Mac），`scrollWidth <= innerWidth`。
- 圖示的說明框文字：GPU 平台「每個方塊 = 1 個 node（N 張 GPU）；未滿一個 node 時只填滿用到的比例；實心為預期需要，虛線為保守估計多出的部分」，Mac 照 v7「每個方塊 = 1 台；實心為預期需要，虛線為保守估計多出的台數」。
- 第 5.1 節的「建議」刻度畫在這組方塊上。

### 5.6.1 「推估」標記改用 Drawer（使用者指定）

第二階段的「推估」popover 把所有推估與未查證的項目全部列出，又附「查看全部依據 →」，內容重複，而且清單一長就超出頁面。改為：

- 滑過或聚焦「推估」：Tooltip 只顯示一行摘要（例如「用到 7 項推估值、3 項未查證；點擊查看」）。
- 點擊：打開「依據」Drawer，最上方篩選預設為「推估與未查證」，可切到「全部」。完整清單只出現在 Drawer。
- 通則：Popover／Tooltip 只放一兩行；清單、表格、多段文字、多欄位表單一律用 Drawer（引用段落用 Modal）。同一份詳細內容只放在一個地方。

### 5.6.1 「推估」：popover 只放摘錄，全部在 Drawer（使用者指定）

第二階段的「推估」popover 把所有推估與未查證的項目全部列出，又附「查看全部依據 →」，清單一長就超出頁面。改為：

- **點擊**「推估」（不用 hover，見第 5.6.2 節）：popover 只放**前 3 項**（對這個結果影響最大的，例如影響瓶頸的那幾項；沒有時依順序），每項一行（名稱加狀態標記，不放長篇依據文字），最後是「查看全部 10 項 →」。popover 有最大寬度，不隨清單變長，過長的文字以省略號截斷。
- 點「查看全部」：打開「依據」Drawer，最上方篩選預設為「推估與未查證」，可切到「全部」。完整清單與細節只在 Drawer。
- 通則：任何可能變長的 popover 都照這個模式——popover 放摘錄，全部內容放 Drawer（引用段落用 Modal）。

### 5.6.2 依使用頻率決定打開方式（使用者指定）

使用者：「設計一個東西要考慮使用頻率，頻率低多幾個步驟展開，誤 hover 機會反而比較多。」這修正主設計 §8.3.3「觸發方式要同時支援 hover、點擊／觸控與鍵盤焦點」的規定：

| 頻率 | 元素 | 打開方式 |
|---|---|---|
| 每次都用 | 句子的空格、答案、每列台數 | 直接顯示，不需要說明框 |
| 選擇時 | 下拉選單中各選項的說明 | 只在選單已打開時，對目前選項（滑鼠或鍵盤）顯示；觸控裝置直接列在選項下方 |
| 偶爾 | 推估摘錄、不可行原因細節、機器圖示圖例、容量條與使用率條的意思、功耗說明、排隊原因、打字示範的近似說明 | **只在點擊、觸控、Enter／Space 時打開**；不用 hover，鍵盤焦點本身也不打開。以細虛底線或小的 `InfoCircleOutlined` 提示可點；點外面或 Esc 關閉 |
| 稽核 | 全部依據、出處、驗證指令、準確度 | 明確的按鈕打開 Drawer |

第二階段的 `Explain` 元件（hover、點擊、焦點都會打開）要依此改寫。

### 5.7 圖示一律用 Ant Design Icons（使用者指定）

- 畫面上不可以用 emoji 或文字符號當圖示。一律改用 `@ant-design/icons`，顏色取自 antd token。
- 目前已知要改的地方：
  - 打字示範等待首字時的「⏳」改為 `HourglassOutlined`（或同系列的沙漏圖示），可以搭配 antd 的旋轉動畫表示「正在等待」。
  - 不可行原因前面的「✗」改為 `CloseCircleOutlined`。
- 實作時要掃過整個 `packages/web/src`（含語系檔），找出其他 emoji 或當作圖示用的符號，一併替換。文案中當標點用的「→」可以保留。

**對照 v7 的完整檢查**：本次實作完成後，用 Playwright 把網站與 v7 原型在同樣的輸入下並排截圖（桌面、手機、淺色、深色），逐項列出差異。凡是和 v7 不同、又不是本文件或主設計明確要求的，都要改回 v7；刻意的差異要在交付時列出理由。

## 6. 動畫設計

### 6.1 共用規則

- 一組 motion token：時長 400 ms，緩動 ease-out（三次方）。D3 與 antd 共用同一組：antd 的動畫 token 透過 `ConfigProvider theme.token` 對齊（例如 `motionDurationMid`、`motionEaseOut`），D3 使用相同的時長與 `easeCubicOut`。
- 同一次輸入改變引起的所有變化同時開始、同時結束，不錯開（主設計 §8.3.1-4）。
- 只有因果變化才動，不做裝飾性動畫（主設計 §8.2-5）。
- `prefers-reduced-motion: reduce` 時，所有時長為 0，直接呈現最終狀態。

### 6.2 每個互動

| 互動 | 怎麼動 | 表達的因果 |
|---|---|---|
| 改人數、工作、模型、精度、速度 | 答案大字與每列台數從舊值滾動到新值；機器圖示長出或縮回；容量條伸縮；以上同時進行 | 「需求變大 → 機器變多」是同一件事 |
| 調整某列的卡數 | 該列的機器圖示長出或縮回；速度、首字數字滾動；容量條伸縮；展開時，使用率條、記憶體條、小圖同步過渡，打字示範立刻改用新速度 | 「多給卡 → 每人變快、可服務人數變多」 |
| 按「建議」還原 | 同上，反方向過渡回建議值 | 回到對照基準 |
| 最佳方案換到另一個平台 | 左側色條與底色從原本那列滑到新的那列（FLIP） | 最划算的平台換了 |
| 某平台由可行變成不可行，或反過來 | 圖示與台數縮回並淡出，「✗ 原因」淡入（或反向）；列高平滑變化 | 參數改變讓這台撐不住或撐得住 |
| 展開／收合一列 | antd `Collapse` 的高度動畫；箭頭旋轉；下方各列平滑位移 | 空間上的連續性 |
| 展開後改人數 | 記憶體條的 KV 格一格格長出或縮回，滿了漸變為紅；使用率條伸縮，瓶頸那根漸變為紅；小圖上的目前位置滑動 | 主設計 §8.3「加人時區塊一格格長出來」 |
| 切換模式 | 句子開頭與結果區交叉淡入淡出；Segmented 滑塊照 antd 原本的動畫 | 換的是問題，不是同一批物件，所以不做位移 |
| 切換語言 | 不做動畫 | 不是因果變化 |

快速連續輸入時，新的過渡從目前畫面上的位置接續，不跳回起點，也不排隊。

### 6.3 所有 UX 狀態變化都要有過渡（使用者指定）

使用者要求：「所有 UX 應當適當添加 transit 動畫。」除了第 6.2 節的因果動畫，畫面上**任何**元素的出現、消失、狀態改變都要有適當的過渡，不可以直接閃現。以下是目前已知的清單，實作時要逐一檢查整個網站，不限於此表：

| 元素 | 過渡 |
|---|---|
| 說明框（Popover／Tooltip）、下拉選單、依據面板（Drawer） | 使用 antd 內建的 motion，正式版不可關閉（測試環境為了 jsdom 關掉 rc-motion 的設定只能存在於測試設定中） |
| 列的展開／收合 | antd `Collapse` 的高度動畫 |
| 「建議」按鈕的選取狀態、調整後才出現的速度行 | 淡入淡出並平滑撐開高度 |
| 人數輸入超出範圍的紅框與提示 | 紅框顏色漸變，提示淡入 |
| 答案行的「推估」「自訂」標記、警告訊息（Alert）、錯誤訊息 | 淡入淡出，高度平滑變化 |
| 模型選單內的可行台數說明（`可在 X / Y 種機台上執行`） | 數字改變時淡入新值 |
| 打字示範 | 換速度時，從目前進度以新速度接續，不閃爍重置 |

時長與緩動一律用第 6.1 節的 motion token；antd 元件以 token 對齊，不各自設定。

## 7. 驗證

- core：`estimatePerformance` 的單元測試，至少涵蓋：
  - 卡數等於建議值時，結果與 `estimateRequirements` 該平台的預期結果一致（同一個切法、同樣的速度與首字）。
  - 卡數增加時，每人速度不會變慢。
  - 卡數少於建議值時，回傳 `ok: false` 與正確的 `why`，並附實際數值（記憶體放得下的情況）。
  - Mac（台）與 GPU 平台各一例；規模上限回傳 `scale`。
- 網站：元件測試涵蓋「建議」按鈕的狀態、調整與還原、網址往返、輸入條件改變時清除調整值、「我已有」模式的新句子與答案。
- **動畫必須在真實瀏覽器驗證**：用 Playwright 在桌面與手機尺寸，對第 6.2 節每一列至少錄一段操作（影片或逐格截圖，例如過渡開始後 0、100、200、400 ms），並交給使用者檢視。jsdom 的 DOM 狀態測試不算動畫驗證。
- 減少動態效果開啟時，所有變化直接到最終狀態（e2e 以 `page.emulateMedia({ reducedMotion: 'reduce' })` 驗證）。

## 8. 留給實作者

- `estimatePerformance` 回傳型別的欄位命名。
- 數字滾動的實作方式（D3 interpolate、CSS 或 antd 的 `Statistic`），只要符合第 6.1 節的時長與緩動。
- 「建議」刻度在機器圖示上的畫法。
- 小圖的尺寸與刻度數量，只要符合主設計 §8.2 的準則。
